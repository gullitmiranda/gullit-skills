# OpenRouter Benchmark and Ranking Research

Accessed: 2026-08-22

## Scope and conclusion

This note is a snapshot of **OpenRouter-published** model metadata, rankings, and documentation. It uses no secondary leaderboard directly. Some OpenRouter benchmark fields are sourced from Artificial Analysis and Design Arena; their provenance is identified by OpenRouter's own Data API rather than independently verified against those providers. [OpenRouter Data API](https://openrouter.ai/docs/cookbook/administration/data-api.md)

OpenRouter provides useful evidence to form a **directional Zed pilot shortlist**, but it does not publish a Zed-agent benchmark, a Zed runtime configuration, or a score for a model/provider/effort/tool-schema tuple. Therefore, none of the data below is sufficient to populate the Provisional Matrix's `Quality`, `Reliability`, `Cost`, or `Latency` cells as measured Zed evidence, and it does **not** justify changing any default. [OpenRouter Models API](https://openrouter.ai/docs/guides/overview/models.md); [OpenRouter Provider Routing](https://openrouter.ai/docs/guides/routing/provider-selection.md)

## What OpenRouter exposes

### 1. Model-catalog benchmark fields

The public `GET /api/v1/models` catalog exposes a model `id`, a stable `canonical_slug`, catalog-added `created` timestamp, current top-provider pricing/capability metadata, supported parameters, default and supported reasoning efforts, and an optional `benchmarks` object. `canonical_slug` identifies the model snapshot; `created` is when OpenRouter added the model, **not** when a benchmark was run. The catalog may change independently of API versioning. [Models API schema](https://openrouter.ai/docs/guides/overview/models.md); [API versioning](https://openrouter.ai/docs/api_reference/versioning.md)

### 2. Usage rankings are not quality rankings

The public [OpenRouter rankings page](https://openrouter.ai/rankings) reported data through **2026-08-21** when accessed. Its displayed top-ten token-usage order was: DeepSeek V4 Flash 0731 (11.7T tokens), Hy3 (8.93T), MiMo-V2.5 (8.18T), GPT-5.6 Luna (5.41T), DeepSeek V4 Flash 0423 (5.20T), Nemotron 3 Ultra (free) (4.08T), GLM 5.2 (3.79T), Claude Opus 5 (2.47T), Ox Alpha (2.00T), and DeepSeek V4 Pro 0423 (1.96T). [OpenRouter rankings](https://openrouter.ai/rankings)

OpenRouter explicitly says these ranks are token volume through its API, not model quality, accuracy, reasoning ability, or benchmark performance. The figures cover OpenRouter traffic rather than the whole market, exclude private requests, and are distorted for cross-model preference comparisons by model verbosity and tokenizer differences. They are operational adoption/context signals only. [OpenRouter rankings methodology](https://openrouter.ai/rankings); [Data API token-comparability limitation](https://openrouter.ai/docs/cookbook/administration/data-api.md)

For a versioned machine-readable usage snapshot, `GET /api/v1/datasets/rankings-daily` returns daily top-50 token totals plus `meta.as_of`, `meta.version` (`v1`), start/end date, and canonical `model_permaslug`; non-default variants are separate rows. It requires an OpenRouter API key. [Rankings Daily API](https://openrouter.ai/docs/cookbook/administration/data-api.md)

### 3. Performance and tool-use evidence is distinct

The model catalog can sort models by p50 throughput and p50 time-to-first-token, but does not return those numeric measurements as fields in the public catalog response. Provider routing supports rolling five-minute p50/p75/p90/p99 latency and throughput preferences; those values are provider- and moment-dependent, rather than model benchmark scores. [Models API sorting](https://openrouter.ai/docs/guides/overview/models.md); [Provider performance thresholds](https://openrouter.ai/docs/guides/routing/provider-selection.md)

OpenRouter standardizes the tool-calling interface, but the model only requests a call: the client/runtime executes it and returns the result. OpenRouter also reports a provider-oriented Tool Call Error Rate on model Performance tabs, but that is not included in the benchmark fields or public catalog snapshot captured here. This makes a Zed pilot's invalid-call rate, stalled-agent rate, and validated-task completion rate indispensable for safe implementation and delivery decisions. [Tool Calling](https://openrouter.ai/docs/guides/features/tool-calling.md)

### Provider, fallback, and runtime portability contract

- **Provider identity:** OpenRouter-managed routing is the portable default, but it is not a reproducible provider pin. OpenRouter can load balance across providers, and endpoint records show that one model snapshot can have different provider tags, capabilities, context limits, prices, and uptime. Pin an exact provider tag only after a privacy, capability, and reliability pilot; otherwise record the actual provider returned by the request. [Provider Routing](https://openrouter.ai/docs/guides/routing/provider-selection.md), [Claude endpoint records](https://openrouter.ai/api/v1/models/anthropic/claude-opus-5-20260723/endpoints), [GPT-5.6 Sol endpoint records](https://openrouter.ai/api/v1/models/openai/gpt-5.6-sol-20260709/endpoints)
- **Tool routing:** All five catalog records advertise `tools` and `tool_choice`, but OpenRouter only standardizes the request/response interface. The client or runtime executes the requested tool and returns its result. Auto Exacto may reorder providers for tool requests using provider-level throughput, tool-call error rate, and benchmark signals; explicitly sorting by price bypasses that optimization. [Tool Calling](https://openrouter.ai/docs/guides/features/tool-calling.md), [Auto Exacto](https://openrouter.ai/docs/guides/routing/auto-exacto)
- **Model fallback:** Use a model fallback list only for routine, planning, or reversible implementation work. OpenRouter charges for the model ultimately used and returns that model in the response. For debugging, review, and delivery, prefer an explicit escalation so a lower-cost or different-model response cannot be mistaken for the selected configuration. [Model Fallbacks](https://openrouter.ai/docs/guides/routing/model-fallbacks)
- **Zed harness versus terminal agent:** The model/effort/provider contract is portable only if both runtimes can send the same tool schema, `tool_choice`, reasoning setting, context, and output constraints. Zed may expose editor/file tools and approval gates while a terminal agent may expose shell tools, process state, and different retry or streaming behavior. OpenRouter data cannot resolve those differences. Pilot both runtimes separately with the same repository tasks and record tool schema, permissions, actual provider, actual model, effort, retries, stalls, validated completion, and billed usage.
- **No runtime change:** This section does not select a Zed default or alter any runtime/profile configuration. It is a policy hypothesis for a later documentation decision only.

No additional candidate is promoted from this snapshot. The five existing records cover a useful value/balanced/specialist/frontier frontier; adding a sixth model without comparable primary fields would weaken rather than strengthen the decision.

## How to record a comparable follow-up

1. Pin the public `id`, retain the `canonical_slug`, and avoid aliases such as `~openai/gpt-latest`; aliases resolve to changing targets. Also record the actual model returned by the runtime. [Models API](https://openrouter.ai/docs/guides/overview/models.md)
2. Record the full configuration: provider selection/fallback policy, model, reasoning effort/thinking mode, model variant, runtime version, tool schema, permissions, and repository state. OpenRouter otherwise load-balances among providers by price and can fall back after errors, so a model ID alone does not uniquely identify the serving configuration. [Provider Routing](https://openrouter.ai/docs/guides/routing/provider-selection.md)
3. Run the same Zed task set for every candidate: a planning task, an implementation task using the expected tools, and a delivery task requiring the project's validation command(s). Record validated completion, invalid tool calls, retries/stalls, elapsed time, and actual billed cost.
4. If the OpenRouter benchmark endpoint can be queried with a valid key, preserve its `meta` block (`as_of`, `version`, source, model count, and source URL) alongside any extracted score. The endpoint's published `as_of` is required to make a benchmark table a reproducible snapshot. [Data API versioning and response metadata](https://openrouter.ai/docs/cookbook/administration/data-api.md)

## Explicit limitations and blockers

- **No authenticated benchmark snapshot:** `GET /api/v1/benchmarks` returned `401 No cookie auth credentials found` in this research environment. OpenRouter documents that the endpoint requires a valid API key. Therefore this note cannot report the endpoint's current `meta.as_of`, `meta.version`, sorted top-N response, or any OpenRouter search-eval run configuration. The public model-catalog records above remain directly accessible, but have no benchmark `as_of` metadata. [Data API authentication requirement](https://openrouter.ai/docs/cookbook/administration/data-api.md)
- **No Zed comparability:** OpenRouter's exposed benchmark categories have no Zed runtime, Zed tool schema, editor state, terminal sandbox, repository, or validation outcome. Design Arena's agent categories are closer than generic model categories, but still do not establish performance in Zed.
- **No benchmark effort/provider pinning:** The composite and Design Arena model records identify a model snapshot, not the catalog default reasoning effort, a provider, fallback behavior, temperature, or tool schema. The default efforts in the candidate table are only deployment hypotheses.
- **Usage is not preference or quality:** the token-usage ranking cannot select a model for any Zed workload, and token totals are not comparable across provider tokenizers. [OpenRouter rankings methodology](https://openrouter.ai/rankings); [Data API token accounting](https://openrouter.ai/docs/cookbook/administration/data-api.md)
- **Catalog metadata can change:** OpenRouter uses stable API version `v1`, allows additive response fields without notice, and treats model availability separately from API versioning. Re-read the live record and preserve the access date before each pilot. [API versioning](https://openrouter.ai/docs/api_reference/versioning.md)
